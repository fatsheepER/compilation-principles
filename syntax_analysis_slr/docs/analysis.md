# 实验 4：SLR(1) 语法分析实现方法说明

本文档根据 `task.md` 中给定的表达式文法，对 SLR(1) 分析所需的增广文法、`FOLLOW` 集、LR(0) 项目集规范族、`ACTION` / `GOTO` 分析表和总控过程进行整理，并结合本仓库前三次实验的结构给出初步程序设计。

本实验继续只完成语法分析：程序判断输入表达式是否属于给定文法，并输出移进、归约过程；表达式求值不属于本次实验的必要内容。

---

## 1. 实验目标

实现一个基于 SLR(1) 分析表的自下而上语法分析程序，完成以下任务：

1. 表示给定表达式文法，并构造增广文法。
2. 求出构造 SLR(1) 分析表所需的 `FOLLOW` 集。
3. 构造 LR(0) 项目集规范族以及项目集之间的状态转换。
4. 根据 LR(0) 项目和 `FOLLOW` 集生成 `ACTION` 表与 `GOTO` 表，并检查冲突。
5. 读取待分析表达式，使用状态栈和符号栈执行移进、归约、接受或报错动作。
6. 输出分析表、项目集、每条表达式的分析结果和分析步骤。

SLR(1) 与实验 3 的算符优先方法都属于自下而上的移进-归约分析，但两者的判定依据不同：

| 方法 | 决策依据 | 归约依据 |
| --- | --- | --- |
| 算符优先分析 | 栈顶终结符和当前输入终结符之间的优先关系 | 最左素短语的终结符边界，非终结符可抽象为 `N` |
| SLR(1) 分析 | 栈顶状态和当前输入终结符对应的 `ACTION` 表项 | LR(0) 归约项目及产生式左部的 `FOLLOW` 集，保留 `S`、`E`、`T`、`F` 的区别 |

因此，本实验不能复用算符优先关系表或 `N + N` 一类的归约匹配策略，而应重新构建 LR 状态机和 SLR(1) 分析表。

## 2. 使用的文法与输入符号约定

### 2.1 作业给定文法

作业给定的文法为：

```text
S -> E
E -> E + T
E -> T
T -> T * F
T -> F
F -> ( E )
F -> i
```

终结符和非终结符集合为：

```text
VN = { S, E, T, F }
VT = { i, +, *, (, ) }
```

分析程序额外使用输入结束符 `#`：

```text
VT' = { i, +, *, (, ), # }
```

其中 `i` 表示一个合法操作数，`#` 只作为输入结束标记，不属于原文法的普通终结符。

### 2.2 与词法分析输出的对接

本仓库已有 `syntax_analysis_common` 公共模块，其中 `Terminal`、`InputToken` 与 `TokenReader` 已经为表达式语法分析提供了统一输入形式。SLR(1) 程序可以直接复用这一公共模块，而不需要重新读取原始源码。

程序默认输入应继续来自：

```text
../lexical_analysis/output/result.txt
../lexical_analysis/output/error.txt
```

已有公共读取器的归一化规则为：

| 词法 token | 种别码 | SLR(1) 终结符 |
| --- | --- | --- |
| `TK_IDENTIFIER`，且 lexeme 为 `i` | 0 | `i` |
| `TK_INT_LITERAL` | 1 | `i` |
| `OP_PLUS` | 200 | `+` |
| `OP_MUL` | 202 | `*` |
| `SEP_LPAREN` | 302 | `(` |
| `SEP_RPAREN` | 303 | `)` |
| `SEP_SEMICOLON` | 301 | 当前表达式结束，并追加 `#` |

如果词法错误文件非空，应停止语法分析并报告词法阶段失败。如果 token 无法映射到上表中的终结符，也应将当前表达式判为错误。

## 3. 增广文法与产生式编号

LR 分析需要增广开始产生式。因为作业已经给出开始符号 `S`，本实验在它之前增加新的开始符号 `S'`：

```text
S' -> S
```

完整的增广文法按如下方式编号：

| 编号 | 产生式 |
| --- | --- |
| 0 | `S' -> S` |
| 1 | `S -> E` |
| 2 | `E -> E + T` |
| 3 | `E -> T` |
| 4 | `T -> T * F` |
| 5 | `T -> F` |
| 6 | `F -> ( E )` |
| 7 | `F -> i` |

编号 `0` 的增广产生式只用于判断接受状态；`r1` 至 `r7` 分别表示按编号 `1` 至 `7` 的产生式进行归约。

需要注意，本实验使用原始的左递归表达式文法。LR 分析可以直接处理这种左递归，因此不需要像 LL(1) 预测分析那样把文法改写为带有 `E'`、`T'` 的形式。

## 4. SLR(1) 分析所需的 FOLLOW 集

### 4.1 为什么 SLR(1) 需要 FOLLOW 集

LR(0) 项目只记录“产生式已经识别到了什么位置”。当某个状态中存在归约项目：

```text
A -> β ·
```

纯 LR(0) 方法会尝试在所有输入终结符上按 `A -> β` 归约，容易产生冲突。SLR(1) 对归约动作进行限制：仅当当前输入符号 `a` 属于 `FOLLOW(A)` 时，才在该状态的 `ACTION[state, a]` 中填入归约动作。

即：

```text
若 A -> β · 位于项目集 Ii 中，
则对每个 a ∈ FOLLOW(A)，填入 ACTION[i, a] = reduce A -> β。
```

### 4.2 FOLLOW 集计算规则

通用的 `FOLLOW` 集计算规则为：

1. 对原开始符号 `S`，将结束符 `#` 加入 `FOLLOW(S)`。
2. 若产生式中出现 `A -> α B β`，则将 `FIRST(β)` 中除 `ε` 之外的终结符加入 `FOLLOW(B)`。
3. 若产生式中出现 `A -> α B β`，并且 `β` 为空或 `β` 能推出 `ε`，则将 `FOLLOW(A)` 加入 `FOLLOW(B)`。

本实验文法没有空产生式，也没有两个相邻非终结符，因此上述规则在本题中表现为：`E` 后出现的 `+`、`)` 直接进入 `FOLLOW(E)`，`T` 后出现的 `*` 直接进入 `FOLLOW(T)`，位于产生式末尾的非终结符继承产生式左部的 `FOLLOW` 集。

为完整说明这一计算过程，本题各非终结符的 `FIRST` 集为：

| 非终结符 | `FIRST` 集 |
| --- | --- |
| `S` | `{ (, i }` |
| `E` | `{ (, i }` |
| `T` | `{ (, i }` |
| `F` | `{ (, i }` |

### 4.3 本实验 FOLLOW 集的推导

由各产生式得到如下约束：

| 产生式 | 得到的约束 |
| --- | --- |
| `S' -> S` | `# ∈ FOLLOW(S)` |
| `S -> E` | `FOLLOW(S) ⊆ FOLLOW(E)` |
| `E -> E + T` | `+ ∈ FOLLOW(E)`，`FOLLOW(E) ⊆ FOLLOW(T)` |
| `E -> T` | `FOLLOW(E) ⊆ FOLLOW(T)` |
| `T -> T * F` | `* ∈ FOLLOW(T)`，`FOLLOW(T) ⊆ FOLLOW(F)` |
| `T -> F` | `FOLLOW(T) ⊆ FOLLOW(F)` |
| `F -> ( E )` | `) ∈ FOLLOW(E)` |

反复传播直到集合不再变化，得到：

| 非终结符 | `FOLLOW` 集 |
| --- | --- |
| `S` | `{ # }` |
| `E` | `{ +, ), # }` |
| `T` | `{ *, +, ), # }` |
| `F` | `{ *, +, ), # }` |

这些集合直接决定归约动作可以出现在哪些终结符列中。例如，项目 `E -> T ·` 只会在 `+`、`)`、`#` 三列填入按产生式 `3` 归约，而不会在 `*` 列归约，从而允许 `T` 后继续移进乘号。

## 5. LR(0) 项目与状态转换方法

### 5.1 LR(0) 项目

对于产生式 `A -> XYZ`，在右部不同位置加入圆点就构成 LR(0) 项目：

```text
A -> · X Y Z
A -> X · Y Z
A -> X Y · Z
A -> X Y Z ·
```

圆点左侧表示当前已经识别的部分，圆点右侧表示后续希望读入或归约得到的符号。圆点到达产生式末尾的项目称为归约项目。

### 5.2 `closure` 运算

若项目集中存在：

```text
A -> α · B β
```

其中圆点后是非终结符 `B`，则分析器接下来可能开始识别 `B` 的任意产生式，因此需要加入所有形如：

```text
B -> · γ
```

的项目，并继续重复这一操作直到不再产生新项目。

### 5.3 `goto` 运算

对于项目集 `I` 和文法符号 `X`，`goto(I, X)` 表示在状态 `I` 中识别一个 `X` 后能够到达的项目集。其构造过程为：

1. 找出 `I` 中所有圆点紧靠在 `X` 前面的项目。
2. 将这些项目的圆点越过 `X`。
3. 对所得项目集合执行 `closure`。

从初始项目集 `closure({ S' -> · S })` 开始，不断执行 `goto`，即可得到 LR(0) 项目集规范族。

## 8. SLR(1) 分析表的构造

### 8.1 ACTION 表填表规则

对于状态 `Ii`：

1. 如果项目集中包含 `A -> α · a β`，其中 `a` 是终结符，且 `goto(Ii, a) = Ij`，则：

```text
ACTION[i, a] = sj
```

表示移进输入符号 `a` 并进入状态 `Ij`。

2. 如果项目集中包含归约项目 `A -> α ·`，且 `A` 不是增广开始符号，则对每个 `a ∈ FOLLOW(A)` 填入：

```text
ACTION[i, a] = rk
```

其中 `k` 是产生式 `A -> α` 的编号。

3. 如果项目集中包含：

```text
S' -> S ·
```

则填入：

```text
ACTION[i, #] = acc
```

4. 未被以上规则填入的表项均为空，分析时遇到空表项表示语法错误。

### 8.2 GOTO 表填表规则

如果 `goto(Ii, A) = Ij`，其中 `A` 是非终结符，则：

```text
GOTO[i, A] = j
```

归约后，分析器弹出产生式右部对应的状态与文法符号，再根据新栈顶状态以及产生式左部非终结符查 `GOTO` 表，压入新的状态。

### 8.3 表中记号

| 记号 | 含义 |
| --- | --- |
| `sj` | 将当前输入符号移进，并将状态 `j` 入栈 |
| `rk` | 按编号为 `k` 的产生式归约 |
| `acc` | 输入串分析成功 |
| 空白 | 当前状态下遇到该输入符号是语法错误 |

### 9.1 关键表项说明

1. `I3` 同时包含 `E -> T ·` 与 `T -> T · * F`。因为 `*` 不属于 `FOLLOW(E)`，所以在 `ACTION[I3, *]` 中只填 `s8`，不会填 `r3`。
2. `I10` 同时包含 `E -> E + T ·` 与 `T -> T · * F`。同理，乘号列填 `s8`，而在 `+`、`)`、`#` 列按产生式 `2` 归约。
3. `I4`、`I6`、`I11`、`I12` 是纯归约状态，归约列分别由 `FOLLOW(T)` 或 `FOLLOW(F)` 决定。
4. `I1` 中只有增广项目 `S' -> S ·`，因此仅在输入结束符 `#` 上接受。

### 9.2 冲突检查结论

按照上述 LR(0) 项目集和 `FOLLOW` 集填表后，每个表格单元最多只有一个动作：

```text
移进/归约冲突：无
归约/归约冲突：无
```

因此，该增广表达式文法是一个 SLR(1) 文法，可直接使用本表完成分析。

## 10. SLR(1) 总控分析过程

### 10.1 栈结构

根据作业要求，分析器维护状态栈和符号栈。初始状态为：

```text
状态栈：0
符号栈：#
输入串：待分析终结符序列 #
```

输出分析步骤时，也可以将两个栈交错显示为：

```text
# 0
# 0 ( 5 i 6
```

无论内部使用两个独立栈，还是使用包含“符号 + 到达状态”的统一栈节点，都应保持同样的移进和归约语义。

### 10.2 移进动作

若当前栈顶状态为 `s`，当前输入符号为 `a`，且：

```text
ACTION[s, a] = sj
```

则：

1. 将终结符 `a` 压入符号栈。
2. 将状态 `j` 压入状态栈。
3. 输入指针前移到下一个终结符。

### 10.3 归约动作

若：

```text
ACTION[s, a] = rk
```

且编号 `k` 的产生式为：

```text
A -> β
```

则：

1. 从符号栈中弹出 `|β|` 个符号。
2. 从状态栈中弹出 `|β|` 个状态。
3. 令弹栈后的状态栈顶为 `t`。
4. 将非终结符 `A` 压入符号栈。
5. 查 `GOTO[t, A] = u`，将状态 `u` 压入状态栈。
6. 归约动作不消耗当前输入符号，下一步仍以 `a` 查表。

SLR(1) 归约必须严格依据产生式右部长度和左部非终结符完成，不能像算符优先实验那样把 `E`、`T`、`F` 都折叠为同一个占位符 `N`。

### 10.4 接受与报错

若：

```text
ACTION[s, #] = acc
```

则当前表达式分析成功。

若 `ACTION[s, a]` 为空，或归约后不存在合法的 `GOTO[t, A]`，则当前表达式存在语法错误。错误信息建议包含：

```text
表达式编号
错误 token 的词素及 token 文件行号
当前状态
当前输入终结符
ACTION 表项为空，或 GOTO 状态缺失的说明
```

## 11. 示例：分析 `(i+i)*i`

以下过程以终结符序列：

```text
( i + i ) * i #
```

为例。栈一列按“符号 状态”的交错形式记录，`# 0` 表示分析开始时栈底符号与初始状态。

| 步骤 | 分析栈 | 剩余输入 | 动作 |
| --- | --- | --- | --- |
| 1 | `# 0` | `( i + i ) * i #` | `s5`，移进 `(` |
| 2 | `# 0 ( 5` | `i + i ) * i #` | `s6`，移进 `i` |
| 3 | `# 0 ( 5 i 6` | `+ i ) * i #` | `r7: F -> i` |
| 4 | `# 0 ( 5 F 4` | `+ i ) * i #` | `r5: T -> F` |
| 5 | `# 0 ( 5 T 3` | `+ i ) * i #` | `r3: E -> T` |
| 6 | `# 0 ( 5 E 9` | `+ i ) * i #` | `s7`，移进 `+` |
| 7 | `# 0 ( 5 E 9 + 7` | `i ) * i #` | `s6`，移进 `i` |
| 8 | `# 0 ( 5 E 9 + 7 i 6` | `) * i #` | `r7: F -> i` |
| 9 | `# 0 ( 5 E 9 + 7 F 4` | `) * i #` | `r5: T -> F` |
| 10 | `# 0 ( 5 E 9 + 7 T 10` | `) * i #` | `r2: E -> E + T` |
| 11 | `# 0 ( 5 E 9` | `) * i #` | `s12`，移进 `)` |
| 12 | `# 0 ( 5 E 9 ) 12` | `* i #` | `r6: F -> ( E )` |
| 13 | `# 0 F 4` | `* i #` | `r5: T -> F` |
| 14 | `# 0 T 3` | `* i #` | `s8`，移进 `*` |
| 15 | `# 0 T 3 * 8` | `i #` | `s6`，移进 `i` |
| 16 | `# 0 T 3 * 8 i 6` | `#` | `r7: F -> i` |
| 17 | `# 0 T 3 * 8 F 11` | `#` | `r4: T -> T * F` |
| 18 | `# 0 T 3` | `#` | `r3: E -> T` |
| 19 | `# 0 E 2` | `#` | `r1: S -> E` |
| 20 | `# 0 S 1` | `#` | `acc`，分析成功 |

这个用例同时覆盖括号、加法、乘法、移进动作、多种归约动作和最终接受状态，适合作为实现后的首个完整回归测试。

## 12. 初步程序设计

### 12.1 设计原则

本实验初步实现应遵守以下原则：

1. 复用已经稳定的 token 输入边界，即 `syntax_analysis_common` 中的 `Terminal`、`InputToken` 和 `TokenReader`。
2. 保持 SLR(1) 专属的文法、项目集、分析表和 parser 位于 `syntax_analysis_slr` 内，不将 LR 语义塞入公共 token 模块。
3. 分析表应由文法、项目集和 `FOLLOW` 集机械构造，并在构造时检测冲突；不建议仅把本文表格硬编码成判断分支。
4. 分析过程和中间构造结果均应可输出到文件，便于后续实验报告直接引用真实运行结果。

### 12.2 建议目录结构

```text
syntax_analysis_slr/
  docs/
    task.md
    analysis.md
    program_design.md        # 实现前可进一步细化

  src/
    main.cpp

    grammar.h
    grammar.cpp

    follow_set.h
    follow_set.cpp

    lr0_automaton.h
    lr0_automaton.cpp

    slr_table.h
    slr_table.cpp

    parser.h
    parser.cpp

    diagnostic.h

    result_writer.h
    result_writer.cpp
```

公共输入模块继续放在：

```text
syntax_analysis_common/src/
  terminal.h
  terminal.cpp
  input_token.h
  token_reader.h
  token_reader.cpp
```

### 12.3 Library 与 Executable 划分

建议延续既有语法分析实验的组织方式：

| 目标 | 职责 |
| --- | --- |
| `syntax_analysis_slr_lib` | 文法、`FOLLOW` 集、LR(0) 项目集、SLR 表、parser、诊断和输出逻辑 |
| `syntax_analysis_slr` | 程序入口、默认路径组织、调用 library 和打印运行摘要 |
| `run_syntax_analysis_slr` | 在 `syntax_analysis_slr/` 目录作为工作目录运行可执行程序 |

后续接入 CMake 时，`syntax_analysis_slr_lib` 应链接 `syntax_analysis_common`，使终结符表示与 token 读取规则不发生复制和漂移。

### 12.4 模块职责

#### `grammar.h` / `grammar.cpp`

负责表示增广文法和产生式编号，至少提供：

```text
非终结符 S', S, E, T, F
终结符 i, +, *, (, ), #
产生式列表与开始符号
符号和产生式的文本输出函数
```

#### `follow_set.h` / `follow_set.cpp`

负责依据文法计算 `FOLLOW` 集，并向输出模块提供集合结果。虽然本实验的集合可以手工写出，实现时仍建议按规则迭代计算，使分析表构造过程与原理一致。

#### `lr0_automaton.h` / `lr0_automaton.cpp`

负责：

1. 定义 LR(0) 项目，例如“产生式编号 + 圆点位置”。
2. 实现 `closure` 与 `goto`。
3. 构造项目集规范族。
4. 保存状态间转换关系。
5. 提供可打印的项目集和状态转换数据。

#### `slr_table.h` / `slr_table.cpp`

负责根据项目集、转换关系和 `FOLLOW` 集构造：

```text
ACTION[state, terminal]
GOTO[state, nonterminal]
```

表项建议采用结构化动作类型：

```text
Shift(next_state)
Reduce(production_id)
Accept
Error
```

构造过程中如果同一表项需要写入不同动作，应记录冲突并拒绝进入正常分析流程。

#### `parser.h` / `parser.cpp`

负责读取一条已经归一化的表达式 token 序列，执行 SLR(1) 总控算法，并记录：

```text
是否接受
错误位置与错误原因
每一步的状态栈、符号栈、剩余输入和动作
```

parser 只通过 SLR 表驱动动作，不应针对 `+`、`*` 或括号写特殊语法分支。

#### `diagnostic.h`

负责组织错误结构与错误类型，例如：

```text
词法阶段失败
token 不属于本实验终结符
ACTION 表项为空
归约后 GOTO 表项缺失
分析表存在冲突
表达式缺少结束分号或为空
```

#### `result_writer.h` / `result_writer.cpp`

建议输出以下文件：

| 文件 | 内容 |
| --- | --- |
| `output/follow_sets.txt` | `FOLLOW(S)`、`FOLLOW(E)`、`FOLLOW(T)`、`FOLLOW(F)` |
| `output/lr0_item_sets.txt` | 项目集规范族与状态转换关系 |
| `output/slr_table.txt` | `ACTION` / `GOTO` 表及冲突检查结果 |
| `output/result.txt` | 每条表达式的接受或拒绝结论 |
| `output/error.txt` | token 错误或 SLR 分析错误的详细信息 |
| `output/steps.txt` | 每条表达式的移进、归约、接受过程 |

### 12.5 整体执行流程

完整流程建议如下：

1. `main` 构造增广文法。
2. `FollowSetCalculator` 计算 `FOLLOW` 集。
3. `LR0Automaton` 构造项目集规范族及转换。
4. `SLRTableBuilder` 生成 `ACTION` / `GOTO` 表并检查冲突。
5. `ResultWriter` 输出集合、项目集和分析表等静态构造结果。
6. `TokenReader` 检查词法错误文件，读取并切分表达式 token 流。
7. 若词法阶段失败，则记录错误并停止逐表达式分析。
8. 对每条合法 token 序列调用 `Parser` 执行 SLR(1) 分析。
9. `ResultWriter` 输出每条表达式的结果、诊断和详细步骤。

## 13. 初步测试规划

实现后至少应覆盖下列测试类别：

| 类别 | 示例输入 | 预期 |
| --- | --- | --- |
| 单个操作数 | `i;` 或 `1;` | 接受 |
| 优先级组合 | `i+i*i;` | 接受 |
| 括号与多次归约 | `(i+i)*i;` | 接受，并产生第 11 节对应的主要动作序列 |
| 右括号多余 | `i+i)*i;` | 拒绝，某状态在 `)` 列 `ACTION` 为空 |
| 运算符连续 | `i+*i;` | 拒绝，读到 `*` 时无法继续移进或归约 |
| 括号缺失 | `(i+i;` | 拒绝，输入结束时无法完成右括号移进 |
| 文法外 token | `i-i;` 或 `x+i;` | 在 token 归一化阶段报告错误 |
| 输入切分错误 | `i+i` | 报告缺少结束分号 |

验证时不仅需要检查最终接受/拒绝结果，还应检查：

1. `FOLLOW` 集输出是否与第 4 节一致。
2. 项目集总数是否为 13，状态转换是否与第 7 节一致。
3. SLR 表是否与第 9 节一致并报告无冲突。
4. `(i+i)*i` 的 `steps.txt` 是否包含移进、归约以及最终 `acc`。

## 14. 本阶段结论

本次实验使用作业给定的原始左递归表达式文法，在增加产生式 `S' -> S` 后可构造出 13 个 LR(0) 项目集。利用：

```text
FOLLOW(S) = { # }
FOLLOW(E) = { +, ), # }
FOLLOW(T) = { *, +, ), # }
FOLLOW(F) = { *, +, ), # }
```

对归约项限制填表后，所得 `ACTION` / `GOTO` 表不存在冲突，因此该文法可以使用 SLR(1) 方法完成语法分析。

在程序结构上，本实验可直接复用 `syntax_analysis_common` 已有的 token 读取与终结符表示模块，同时在 `syntax_analysis_slr` 中独立实现 `FOLLOW` 集、LR(0) 自动机、SLR 分析表和状态驱动 parser。这样既保持了输入边界的一致性，也能清晰反映本实验与算符优先分析方法在核心算法上的区别。
